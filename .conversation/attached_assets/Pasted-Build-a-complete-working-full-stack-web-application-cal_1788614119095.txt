Build a complete working full-stack web application called *HONEY CHAIN* — an AI + Blockchain based Honey Traceability and Smart Beekeeping Management System.

This is an MVP for a college hackathon, so prioritize a working end-to-end application over unnecessary complexity.

## 1. TECHNOLOGY STACK

Frontend:

* HTML
* CSS
* JavaScript
* Bootstrap if useful
* Chart.js for charts

Backend:

* Python
* FastAPI
* REST APIs

Database:

* MySQL
* SQLAlchemy ORM

Blockchain:

* Implement a simple permissioned blockchain/hash ledger in Python for the MVP.
* Use SHA-256 hashing.
* Each blockchain block/transaction must contain:

  * transaction_id
  * batch_id
  * event_type
  * timestamp
  * data_hash
  * previous_hash
  * current_hash
  * actor/user_id
* The blockchain must be append-only.
* Do NOT allow editing or deleting confirmed blockchain transactions.
* Implement blockchain verification by recalculating hashes and checking the chain.
* Store blockchain transaction metadata/hash in the database as well so the application can retrieve it easily.
* Do NOT store complete sensitive/application data directly on blockchain.
* Detailed application data remains in MySQL.
* Blockchain provides tamper-evident proof of important events.

QR:

* Python QR-code library.
* Generate a QR code linked to the public batch verification page.

AI/ML:

* Python
* Pandas
* NumPy
* Scikit-learn
* Simple honey-yield prediction model.

# 14. BLOCKCHAIN IMPLEMENTATION

Create a Python blockchain module.

Implement:

### Block class

Each block contains:

* index
* timestamp
* transaction
* previous_hash
* hash

### Blockchain class

Implement:

* create_genesis_block()
* add_transaction()
* calculate_hash()
* get_chain()
* verify_chain()

Use SHA-256.

Example conceptual chain:

GENESIS
↓
BLOCK 1
Batch Created
↓
BLOCK 2
Harvest Recorded
↓
BLOCK 3
Quality Verified
↓
BLOCK 4
Processed
↓
BLOCK 5
Packaged
↓
BLOCK 6
Shipped

Each block contains:

previous_hash → current_hash

Therefore, if someone changes the contents of an old block, its hash will no longer match the next block's previous_hash.

The application must provide a:

*"Verify Blockchain"*

button.

When clicked:

* Check every block.
* Recalculate its hash.
* Compare with stored hash.
* Compare previous_hash.
* Return:

"Blockchain Valid ✓"

or

"Blockchain Tampered ✗"

# 15. TRANSACTION CORRECTION SYSTEM

IMPORTANT:

A confirmed blockchain transaction must NEVER be edited or deleted.

If an authorized user makes a mistake, implement:

### Correction Request

Example:

Original:

Harvest Quantity = 12 kg

User wants:

Harvest Quantity = 15 kg

Do NOT change the old blockchain transaction.

Instead create:

CORRECTION_TRANSACTION

Containing:

* correction_id
* original_transaction_id
* batch_id
* old_value
* new_value
* reason
* corrected_by
* timestamp
* correction_hash

Then create a new blockchain block.

Example:

BLOCK 10
Original:
Quantity = 12 kg

BLOCK 11
Correction:
12 kg → 15 kg
Reason = Measurement error
Changed by = User123

The old transaction remains permanently visible in the audit history.

The application should show:

Original Record
↓
Correction
↓
Current Valid Record

# 30. IMPORTANT EXPLANATION FOR THE MENTOR

The UI should have an "Architecture / About Blockchain" section explaining:

"Detailed application data is stored in MySQL. Important supply-chain events are hashed and recorded in an append-only blockchain ledger. Each block contains the hash of the previous block, making unauthorized modification detectable. Blockchain is therefore used for tamper-evident traceability and auditability, not as the primary database."

Do NOT claim that the entire application database is stored on blockchain.
